SmartLearning 後端 · M01 登入測試

這份說明是帶你安全地測試登入

測試會用一個暫時建立、與日常資料分開的資料庫，確認登入、保持登入和登出都正常。現在程式和測試材料已備妥，但實際資料庫測試還沒有執行，所以目前不能說測試已通過。

測試程式已備妥實際資料庫測試：尚未執行

先認識這次會做什麼

可以把「登入狀態」想成一張臨時通行證。登入後，系統把通行證放在瀏覽器的安全小盒子裡，之後用它確認你仍是同一位使用者。登出時，系統會讓這張通行證失效。

  • 正確帳密：可以登入，拿到安全的登入證明。
  • 錯誤帳密或不符合使用資格：都會得到相同的拒絕結果，避免別人猜出哪些帳號存在。
  • 缺少必要的安全確認，或從不允許的網站送出修改：系統會拒絕。
  • 登出後再拿舊證明來：系統會拒絕。

測試也會確認資料庫只保存通行證的保護後版本，不保存可直接使用的原始內容。

這次不測：登入多久會自動失效的時間邊界，以及其他功能停用角色後能否立刻取消登入。這些需要另外安排測試。

開始之前：先停下來確認

這次操作會建立暫時的資料庫資源、調整資料庫結構、放入少量測試資料，完成後再只清掉本次建立的測試資料。這些都會改變環境，所以必須先取得明確核准。

  1. 確認核准範圍。核准要清楚包含新建暫時測試資料庫、調整資料庫結構、寫入測試資料，以及清理這些測試資料。這份說明本身不代表已取得核准。若要刪除資料庫儲存空間，還要另外同意。
  2. 確認位置。在後端專案的主要資料夾執行。不要清除、還原或暫存目前已有的工作變更。
  3. 確認測試設定。.env.test 應只連到本機的 smartlearning_test，並具備已核准的安全設定。不要貼出或分享這個檔案。
  4. 先做不改資料的檢查：
npm run db:test:preflight

若檢查失敗、目標不清楚、連接埠已有人使用、設定連到其他資料庫，或發現舊的測試資源，請停下來。不要改用日常開發資料庫，也不要先刪東西再試。

只有核准後才建立全新的測試資料庫：

npm run db:test:up

等畫面明確出現 Clean test database verified，並記下本次的 run_id（本次執行的識別號）。如果失敗，先保留現況供檢查；不要自行重開、重建或刪除資源。

執行登入測試

把剛才得到的識別號填進下方指令。請使用本次實際顯示的號碼，不要沿用之前的。

RUN_ID='<填入本次顯示的 run-id>'
npm run db:test:assert-integration -- "$RUN_ID"

這一步只檢查目標是否正確。它會確認資料庫確實屬於這次建立的測試環境、狀態正常、資料表是空的，並確認資料庫結構已準備好。必須看到 Integration target PASS 才能繼續。若失敗，請停下來，不要手動改資料庫。

接著執行真正的登入測試：

TEST_DB_RUN_ID="$RUN_ID" NODE_ENV=test npm run test:integration -- --runTestsByPath test/auth.integration-spec.ts

測試程式會自己產生暫時帳號和密碼，建立測試資料，透過真正的網頁服務完成登入與登出，再檢查資料庫結果。密碼只在程式執行時短暫使用，不會寫進檔案或顯示出來。

通過條件：三種情況都要成功：正常登入及登出、錯誤登入得到一致回覆、安全檢查不通過時遭到拒絕。若開始前檢查或結束清理失敗，整次測試都不能算通過。要看到實際測試總結才能判定結果。

完成後再確認測試資料已清除、資料庫回到空白狀態：

npm run db:test:assert-integration -- "$RUN_ID"

如果測試中斷、清理失敗或最後檢查沒通過，記下識別號和不含機密的錯誤摘要，再用以下指令查看狀態：

npm run db:test:status -- "$RUN_ID"

不要手動刪資料、清空整個資料庫、清除所有 Docker 資源，或使用會連儲存空間一起刪除的指令。下一次正式測試應建立全新的隔離環境。

怎麼判斷結果

全部符合才算通過

  • 實際執行整合測試，而且每個案例都通過。
  • 測試前後都確認是同一個正確的暫時資料庫。
  • 確認登出後通行證失效，測試資料也已清掉。

以下情況都還不能算通過

  • 沒有核准、沒有新建測試環境，或測試根本沒跑。
  • 只做了不連資料庫的單元測試、程式檢查或編譯。
  • 工具、Docker 或資料庫出錯，但原因還沒弄清楚。

請記下本次識別號、程式版本、時間、執行指令、測試結果和清理結果。不要記錄或貼出密碼、登入證明、安全確認碼、瀏覽器保存的登入資料、完整設定檔或含個人資料的資料列。

目前進度：登入測試程式和測試資料準備好了；但這次尚未啟動 Docker、調整資料庫或寫入測試資料。因此 PostgreSQL（資料庫）的整合測試目前是尚未執行，不能說整個檢查已完成。

這個測試檔案從頭到尾做什麼

測試檔案像一位按步驟做檢查的人。它先確認自己連到正確的臨時資料庫，再開啟網站、準備幾種測試帳號，最後逐項試登入和登出。每一步都要符合預期，測試才會通過。

開始前先確認資料庫：測試需要你提供本次臨時資料庫的識別號。沒有識別號就停止；識別號對應的資料庫若不是 smartlearning_test 和 app 這個資料區域，也會停止。確認時也會要求測試資料表是空的，避免碰到別人的資料。

接著打開網站：測試在記憶體中啟動真正的網站程式，並打開它需要的 cookie 處理功能。它從設定中取一個允許的網站來源，之後測試會用這個來源送出登入和登出要求。

測試結束一定清理：它只刪本次自建的登入紀錄、角色關聯、測試帳號和測試角色，然後關閉網站。若清理出錯，測試會報錯，不會假裝一切完成。

測試準備了哪些帳號

程式會一次準備四個互不相同的帳號，讓它能分辨「正常帳號」和幾種不該登入的狀況。帳號都是臨時資料，使用特別保留的測試郵件尾碼，不是實際使用者的信箱。

四個帳號共用一個由程式隨機產生的測試密碼。密碼先經過不可直接還原的保護處理，再存入測試資料庫；原始密碼只供這次測試在記憶體裡使用，不會寫入檔案或命令列。

準備資料時，程式把新增動作包在一次資料庫工作裡：建立「老師」角色，再建立四個帳號，並只替需要角色的帳號加上關聯。這樣準備到一半出錯時，不會留下半套測試資料。

三組測試逐項說明

一、正常登入、保持登入，再登出

  1. 先向網站拿一個安全確認碼。
  2. 送出正常帳號、測試密碼、允許的網站來源和確認碼；預期得到成功回覆。
  3. 確認成功回覆只有「已登入」和新的安全確認碼，沒有把密碼回傳。
  4. 確認網站給了瀏覽器一張名為 sl_session 的登入證明，而且瀏覽器腳本不能直接讀它。
  5. 網站資料庫裡找到相符的登入紀錄，確認紀錄屬於正常帳號且仍有效；資料庫存的是保護後的內容，不是 cookie 裡原始的通行證。
  6. 帶著這張證明查詢登入狀態，預期成功。
  7. 帶著允許的來源和更新後的確認碼登出，預期成功且不再回傳內容。
  8. 確認資料庫紀錄已改成「已撤銷」並記下撤銷時間；再查登入狀態，預期遭拒。

二、各種錯誤登入都得到同一種回覆

程式依序試：停用帳號、信箱未確認、沒有角色、錯誤密碼，以及根本不存在的隨機帳號。每次都先拿新的安全確認碼，再送出登入要求。五次都應得到相同的拒絕狀態和相同內容，不能讓人從回覆猜出帳號是否存在或為何不能登入。測試也會比較前後登入紀錄數量，確認失敗沒有偷偷建立登入紀錄。

三、缺少安全確認或來源不可信就拒絕

程式試兩種登入錯誤：不附安全確認碼，以及使用不在允許清單內的網站來源。接著試一次不附安全確認碼的登出。三次都應被拒絕，且不應改動登入狀態。

這些檢查的意思：它不只看畫面上有沒有顯示成功，也直接核對網站回覆和資料庫裡實際留下的紀錄。

測試完成後會留下什麼

  • 整合測試本身不會刪除整個測試資料庫，只會清理由它建立的指定資料。
  • 清理時先刪本次帳號的登入紀錄，再刪角色關聯和帳號，最後刪本次建立的老師角色。
  • 每個刪除都按照本次建立的識別號限定範圍，不會用「刪掉所有資料」的方式處理。
  • 網站程式關閉後，測試才結束；清理失敗會讓測試結果失敗。

因此測試完成後，還要再跑一次資料庫目標檢查，確認資料表回到空白狀態。若中途被中斷，不能假設資料已清乾淨，應先查看狀態並保留錯誤摘要，不要手動擴大清理範圍。

測試帳號不用手動建立

這次的測試帳號由測試程式自動建立並在結束時清理，不需要自己新增帳號。

_plans/m01-first-admin-bootstrap-guide.html 是另一份說明，談的是如何建立正式環境的第一位管理者。那件事和本次暫時測試帳號不同，仍需另外確認與安排。

若不確定某個指令是否安全，先停下來確認目前所在專案、使用的設定和核准範圍。結果以本次實際顯示的訊息為準。

簡單記住：先核准、再確認環境、執行測試、檢查清理。沒有看到實際結果，就不要把它記成通過。

SmartLearning Backend · M01 / Checkpoint B

準備測試帳號，執行 Login 驗收

這份手冊現在聚焦於如何在一次性隔離測試資料庫中，安全建立最低權限的測試帳號並執行真實 HTTP／PostgreSQL 驗收。測試帳號由整合測試短暫建立與清除，不需要人工取得或保存帳密。

資料庫整合測試：需另行核准角色：TEACHER不使用 SYSTEM_ADMIN

這次測試會做什麼

Checkpoint B 範圍

整合測試會先確認指定 run 是本機新建、隔離且完成 migration 的 `smartlearning_test`／`app` 資料庫，並確認應用資料表目前全空。之後測試程式在交易中建立臨時 `TEACHER` 角色與幾個唯一測試帳號；成功帳號設為啟用、Email 已驗證並使用 Argon2 雜湊密碼。它不建立管理者、不建立公開 API，也不配置任何權限映射。

  • 真實 NestJS HTTP 路由、CSRF／Origin guard、cookie 與 Prisma/PostgreSQL repository。
  • CSRF bootstrap、登入成功、登入 Session 驗證、登出及登出後拒絕舊登入 Session。
  • 不存在、停用、未驗證、沒有啟用角色及密碼錯誤均回覆一致的登入失敗。
  • 測試帳號、角色、登入 Session 僅以本次建立的精確識別碼清理；秘密不輸出。
基線變化：整合測試寫入資料後，資料庫不再符合「乾淨基線」。套件會精確刪除自己建立的 fixture；若測試或清理中斷，不能假設資料庫仍乾淨，必須唯讀檢查並改用新 run，不能廣泛清空。

重要區分：測試帳號不是第一個管理者

Checkpoint B 測試帳號

  • 只為 Login／Session／Logout 驗收服務。
  • 由 `test/auth.integration-spec.ts` 在測試開始時隨機產生，測試結束精確清除。
  • 只指派 `TEACHER`，不建立授權映射，不給 `SYSTEM_ADMIN`。
  • 不需要人員複製帳號或密碼，命令列也不帶秘密。

正式第一個系統管理者

  • 屬於部署／維運初始化流程，不是 Checkpoint B fixture。
  • 必須以正式核定的受控 bootstrap 建立，且帳號與 `SYSTEM_ADMIN` 關聯同一交易完成。
  • 執行身分、正式命令、初始秘密交付、有效期、首次登入及入口停用仍依部署契約核定。
  • 目前 checkout 沒有可查證的正式 bootstrap 原始碼；不要執行 `npm run bootstrap:admin` 或 `npm run bootstrap:w1-teacher`。
禁止替代操作：不要手動 SQL、不要將正式帳號流程用在測試 DB，也不要將 development／production／共用 DB 指向測試程式。測試資料只能由新增的測試專用 fixture 建立。

執行前核准與準備

Docker／DB 寫入需另行授權
  1. 先取得明確核准：核准建立新的隔離 Docker 測試 DB、套用 Prisma migrations、寫入並清除短暫測試資料，以及保留／清理本次資源的範圍。這份文件不構成操作授權；volume 刪除永遠需要另行核准。
  2. 確認工作目錄與設定：位於 backend repository 根目錄；`.env.test` 必須存在且只指向 localhost 的 `smartlearning_test`，不要貼出或輸出檔案秘密。必需有核准的 `COOKIE_SECRET`、精確的 `CORS_ORIGIN` 及符合契約的 Session 設定。
  3. 執行唯讀 preflight：
npm run db:test:preflight

preflight 檢查 Docker context／Engine、5432 port、Postgres image、test DB 設定及殘留資源；任何一項不符就停下。不可為了通過檢查而切換到 dev DB、刪除舊 volume 或重用舊 run。

  1. 建立全新隔離測試資料庫：只有核准涵蓋 Docker 建立與 migration 時才執行下列命令。
npm run db:test:up

等待輸出 Clean test database verified，抄下輸出的 run_id。若畫面只看到 Compose project，例如 sltest-20261114113654-e98890d8，它不是 run ID；去掉開頭的 sltest-，此例的 RUN_ID 是 20261114113654-e98890d8。

若需要從本機 run 狀態檔查已記錄的 ID，在 repository 根目錄執行唯讀指令：

find "${XDG_STATE_HOME:-$HOME/.local/state}/smartlearning/test-db/runs" -maxdepth 1 -type f -name '*.json' -printf '%f\n'

每個輸出的檔名去掉最後的 .json 就是 RUN_ID。若沒有輸出，先確認建立工具的輸出與 XDG_STATE_HOME；不要猜 ID、重建、resume 或刪除資源。若建立失敗，保留現場供診斷；只有工具明確回報可安全 resume 時，才依精確 run ID 和 README 規則續跑。

本次核准 DB 的身份：run 專屬 Compose project、PostgreSQL `smartlearning_test`、`app` schema、localhost port 5432。實際以當次工具輸出與唯讀檢查為準；不沿用過去執行的容器／volume 身分。

執行真實整合驗收

測試會自動建立短暫帳號
  1. 先確認精確 run 仍可用：將尖括號換成本次建立時輸出的 run ID。這項唯讀檢查確認 run 記錄、Docker project／container、健康狀態、DB 身分、migration ledger，並拒絕已有應用資料列的資料庫。
npm run db:test:assert-integration -- <run-id>
  1. 執行 Checkpoint B PostgreSQL／HTTP 測試：維持在 repository 根目錄，將相同 run ID 設定給測試程序。不要把帳密、cookie 或 token 放進命令。
TEST_DB_RUN_ID=<run-id> NODE_ENV=test npm run test:integration -- --runTestsByPath test/auth.integration-spec.ts

測試開始前會再次執行精確 run 身分與乾淨資料檢查；缺少 run ID、DB 設定不符、容器不健康、migration ledger 不完整或資料庫不是乾淨基線時會拒絕寫入。測試帳密在記憶體中隨機產生，不會列印或存入版本控制。測試結束會精確清除本次建立的角色、帳號與登入 Session。

預期：三個整合案例通過，分別涵蓋成功登入／Session／登出撤銷、一般化登入失敗、CSRF／Origin 拒絕。任何 setup、HTTP、DB assertion 或 cleanup 失敗都算失敗；不能只看最後一行或把部分結果標成完整 PASS。

  1. 確認 fixture 已清除：再次執行只讀精確 run 檢查；應回報通過。若檢查因殘留應用列而失敗，停止，不可手動清表或重用該 run。
npm run db:test:assert-integration -- <run-id>

如果測試被中斷或清理失敗，保留錯誤與 run ID，先唯讀檢查 `npm run db:test:status -- <run-id>` 和必要的 logs；下一輪使用新的 disposable run。不要執行 prune、`down -v`、全庫清除或 wildcard cleanup。

測試結果如何回報

可記錄

  • Run ID、repository revision、命令、時間與各測試案例狀態。
  • DB 名稱／schema、migration 數、容器健康摘要。
  • HTTP status、DB fixture 是否精確清除，以及是否產生 session 撤銷資料。

不可記錄

  • `.env.test` 內容、資料庫密碼、COOKIE_SECRET。
  • 明文測試密碼、`sl_session` cookie、CSRF token 或完整 cookie jar。
  • 含個資或完整資料列的 DB dump、完整內部錯誤回應。
狀態區分：只有本次整合 suite、DB assertions 與 fixture 清理全部通過，才可把對應 Checkpoint B 認證整合案例記為 PASS。未獲准執行 DB、未建立新 run 或 suite 未跑時記為 BLOCKED／NOT RUN。既有 unit tests、mock API tests、build 或 OpenAPI smoke 不等於此項整合驗收。

與 Checkpoint B 測試手冊銜接

自動 Checkpoint B HTTP／PostgreSQL 整合測試會使用短暫 fixture，帳密不會提供給人工登入。若要在瀏覽器手動驗證 `/login`，請另建專用本機 UI 測試 DB，依 `tools/test-db/README.md` 執行 `npm run db:test:ui-account:create -- <run-id>`；工具會提示輸入 Email、姓名與兩次隱藏密碼，成功後以你輸入的 Email／密碼登入。這個持續測試帳號只具 `TEACHER`，不授予 `SYSTEM_ADMIN`。

佈建後該 DB 不再是乾淨基線，不可用於自動整合測試；自動測試請建立另一個全新 run。手動驗收完成後，可用 `npm run db:test:ui-account:revoke -- <run-id>` 精確停用帳號並撤銷 sessions。忘記密碼／重設 API 已新增；須先套用 email outbox migration 並設定 Gmail SMTP、前端重設 URL 與 outbox encryption key，才會排程寄送。正式帳號與第一位系統管理者仍須依核准流程建立。

操作依據：`tools/test-db/README.md`、`tools/test-db/db-test-env.cjs`、`tools/test-db/assert-integration-ready.cjs`、`test/auth.integration-spec.ts`、`src/auth/auth.controller.ts`、`src/auth/auth.service.ts`、M01 Bootstrap 規格。命令僅在目前 checkout 對應程式與設定存在、操作獲核准且 preflight 通過時適用。

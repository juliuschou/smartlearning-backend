# 後端開發規則：錯誤、重送、分頁與資料更新

這份規則適用於新增或修改後端 API、服務與資料存取功能。目標是讓 API 好理解、重試不會多做一次、清單不會一次撈太多資料，也不會讓一個人的舊修改蓋掉別人的新修改。

動手前先看專案目前的寫法和對外契約；新功能盡量沿用既有格式。若舊作法有安全或資料正確性問題，不要默默改壞相容性，先說明影響和建議。

## 0. 名稱要照 GLOSSARY，讓前後端說同一種話

- 新增或修改功能、API、DTO、欄位和文件前，先查這份權威詞彙表：`/home/user/projects/smartLearning/docs/智學互動平台/20_系統分析/GLOSSARY.md`。
- 名稱一律採用 GLOSSARY 的正式用詞；表中標示為 Avoid 的名稱不要拿來指同一個概念。不要為了同一件事在後端、Swagger 文件和前端各取不同名字。
- 如果找不到適用詞彙，或現有名稱和 GLOSSARY 衝突，先指出來並建議補詞或修正；不要自行發明另一個同義名稱。
- API 文件是前後端共同依據。使用 `@nestjs/swagger` 描述 API 契約，讓前端從 Swagger 文件在 `packages/api-client` 自動產生呼叫 API 的程式碼；不要另外手寫一套內容不同的 API 型別或呼叫定義。
- API 有變更時，Swagger 文件要一起更新，並確認 `packages/api-client` 能依更新後的文件產生正確呼叫程式碼。文件描述必須符合實際行為，不可寫出程式尚未提供的功能。

## 1. Swagger 文件要說清楚 API 契約

- 新增或修改 API 時，使用 NestJS `@nestjs/swagger` 描述實際的輸入和輸出格式，以及成功與重要錯誤回應的 HTTP 狀態碼。
- 清單 API 要寫清楚分頁參數、每頁上限、排序方式、下一頁的取得方式，以及回應中的分頁資訊。
- 若 API 使用冪等識別碼或版本標記，要寫清楚它放在哪裡、如何使用，以及重複請求或版本過期時會回什麼結果。
- Swagger 範例也要遵守安全規則：不可暴露帳號是否存在、密碼、token 或其他敏感資料。
- 任何對外契約變更，都要同步更新 Swagger 描述，並確認 `packages/api-client` 可以從更新後的 Swagger 文件產生正確的 API 呼叫程式碼。若專案尚無可用的產生流程，先說明阻礙，不要假裝已驗證成功。

## 2. 錯誤回覆要固定，也不能洩漏內部資料

- API 發生錯誤時，使用專案共用的錯誤回覆格式，不要每個端點各寫一套。格式至少要讓呼叫端看得出穩定的錯誤代碼和可以顯示給使用者的訊息；需要時附上 request ID，方便查伺服器紀錄。
- 對外訊息要簡單、安全，不回傳程式堆疊、SQL、檔案路徑、秘密、完整內部錯誤或其他不該公開的資訊。
- 真正的原因可以記在伺服器紀錄中，供除錯使用；但不要記錄密碼、token 等秘密，也不要把敏感資料寫進一般 log。
- 同一類錯誤應有一致的 HTTP 狀態碼、錯誤代碼和回覆格式，前端才不必猜每個端點的規則。

## 3. 不要讓人靠錯誤訊息猜出帳號或資料是否存在

- 在登入、忘記密碼、註冊等可能被用來探測帳號的功能，不要明確回覆「這個帳號存在」或「這個帳號不存在」。使用不洩漏差異的通用訊息。
- 對受保護的資料，也要檢查回覆是否會讓未授權的人猜出資料存在與否；需要時讓「不存在」和「不能查看」的對外回覆一致。
- 不代表所有錯誤都要藏起來。只在有被探測或洩漏的風險時採用通用回覆，並保留伺服器內部診斷紀錄。

## 4. 同一個操作重送，不要重複造成結果

網路中斷或使用者重按時，請求可能會送到不只一次。對建立資料、付款/結算、批次處理或其他會造成副作用的操作，設計好如何辨認「這是同一個請求」；例如使用 idempotency key（冪等識別碼）。

- 同一個識別碼、同一份操作內容再次送來時，不要再做一次；回傳第一次處理的結果，或依 API 契約回傳同等結果。
- 同一個識別碼卻帶著不同內容時，要明確拒絕或回報衝突，不能把兩個不同操作當成同一件事。
- 檢查同時送來的重複請求也不會各自成功執行。辨認與執行操作要有可靠的資料庫唯一限制、交易或其他原子保護，不能只靠程式先查一次「有沒有做過」。
- 單純讀取資料通常不用加冪等識別碼。

## 5. 清單要分頁，並限制每次回傳的筆數

- 可能累積很多資料的清單 API，必須分頁；不可沒有上限地一次查完、回傳整張資料表。
- 設定合理的預設每頁筆數和最大筆數，並檢查呼叫端傳入的分頁參數。
- 排序要穩定：若主要排序欄位相同，要再用唯一欄位（例如 ID）排出先後，避免翻頁時資料重複或漏掉。
- 清楚定義下一頁怎麼取得，以及回覆裡有哪些分頁資訊。資料量大或經常變動時，優先評估 cursor pagination（游標分頁）；使用 offset pagination（筆數位移分頁）時，確認它適合這個清單。

## 6. 更新資料時檢查版本，避免互相覆蓋

- 多人或多個請求可能同時修改的資料，更新前要檢查資料是否仍是呼叫端讀取時的版本。可以用 version 欄位、ETag 或其他等效方式。
- 更新時必須在同一個原子操作中確認版本相符並寫入新值；成功後更新版本。不能先查版本、之後再無條件更新，因為兩個請求可能在中間同時通過檢查。
- 如果版本已經過期，不要覆蓋較新的資料；回覆一致的衝突錯誤，讓呼叫端重新讀取後再決定怎麼修改。
- 新增測試確認：兩個人讀到同一版本時，先完成的一方可成功，另一方會收到衝突，而且先完成的資料不會被蓋掉。

## 7. 新增或修改功能時的檢查

依照功能適用的項目，確認並補上測試：

- 名稱符合權威 GLOSSARY，沒有自行改用 Avoid 名稱或另造同義詞。
- Swagger 文件完整反映 API，且 `packages/api-client` 可依該文件產生正確的呼叫程式碼。
- 對外錯誤格式一致，且沒有回傳內部細節或秘密。
- 帳號或受保護資料的回覆不會洩漏其存在與否。
- 重送請求不會重複執行副作用；同 key 不同內容會被拒絕或回報衝突。
- 清單有筆數上限、分頁正常，排序穩定。
- 舊版本更新會被拒絕，不會蓋掉新資料。

若某項不適用，簡單記下原因。只有資料庫欄位（例如 `idempotency_key` 或 `version`）不代表功能已完成；還要確認實際程式有正確檢查、處理併發並回傳預期結果。
